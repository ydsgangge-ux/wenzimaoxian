====================================================================
一、这个产品是什么
====================================================================

一个面向"创作者"的工具，用来写类似以下类型的纯文字互动叙事游戏：
- 《Lifeline》系列：延迟消息流、角色隔一段时间才回复、模拟失联/求生通讯
- 《如果明天是晴天》：多周目、平行世界线，玩家一周目只能看到自己
  所在世界线的事件，需要多周目拼凑全貌
- 文字版《命运石之门》《Re:Zero》式叙事：全局数值累积（收束率、
  好感度）驱动分支，死亡回归/重来机制

产品定位（重要，不要跑偏）：
- 这是一个"创作工具"，不是游戏本身。工具产出的是创作者自己的
  故事，创作者自己决定去哪里发布、怎么变现。
- 不做 Fate/stay night 那种立绘+对话框的传统视觉小说，不做
  图片/BGM 渲染层。专注纯文字消息流形态，这是刻意的范围收窄。
- 商业模式：工具本身免费开放（写作、预览、导出网页版全部免费），
  收费点在"打包/发布服务"（导出独立APK、代上架应用商店/小程序）。
  这意味着工具不碰用户支付、不做内容审核、不接触创作者的收入，
  责任边界清晰。这一点在做发布相关功能时要记住，不要把支付/
  分成逻辑做进产品里。
- LLM 增强模式的 API 成本由玩家自己承担：玩家自己去申请
  DeepSeek/智谱等的 API Key，填入后启用"自由输入"模式。
  Key 只存本地浏览器 localStorage，绝不能经过任何服务器中转，
  这是硬性安全要求，不是"以后再说"的事项。

====================================================================
二、核心设计原则（决定了整个架构，务必先理解再动代码）
====================================================================

原则1：选项模式和自由输入模式，必须共用同一套节点/跳转数据结构

这是最重要的架构决策，来自实际讨论中的一个教训：一开始想先做
"选项模式"再"加"自由输入模式，但意识到如果两者数据结构不同，
后续融合会很痛苦。所以从一开始就把两种交互方式统一成同一个
"节点(Node) -> interaction -> 若干条边(edge)，边指向下一个节点"
的模型，区别只在于"由谁/怎么决定走哪条边"：
- choice 类型：玩家点击，直接走某条边
- freeform 类型：玩家打字，LLM 做意图分类，从预设的几条边里选
  一条最接近的走（LLM 不生成剧情内容，只做路由分类，这样成本
  低、稳定、剧情质量始终由创作者把控，不会跑题或失控）

原则2：LLM 是"翻译/路由"，不是"编剧"

自由输入模式下，LLM 调用只做一件事：判断玩家这句话最接近创作者
预设的哪个"意图选项"，返回对应的序号。不会让 LLM 现场生成剧情
文本或决定剧情走向本身。这保证了：
(a) 剧情质量和一致性始终由创作者的文本控制
(b) 调用成本极低（返回几个 token 就够，不是生成长文本）
(c) 不会因为 LLM 幻觉/跑题而破坏叙事逻辑

原则3：石之门/Re:Zero/如果明天是晴天，本质是同一套底层机制的
不同包装

不要为每个"流派"单独做功能。这几个作品的核心机制拆解后是同一
个东西：全局变量 + 条件跳转 + （未来可能需要的）跨周目持久化。
石之门包装成"收束率"，Re:Zero包装成"死亡回归"，如果明天是晴天
包装成"平行世界线只能看到自己的分支"——工具只需要提供变量/
条件跳转这个通用原语，具体怎么包装成什么叙事概念，是创作者
自己在文本里决定的事，不是工具要单独实现的功能。

当前状态：变量 + 条件跳转（单周目内）已经做了并验证通过。
跨周目持久化（存档点重来后记得之前的选择）尚未实现，
是有意暂缓的——等真正需要写这类剧情时再加，避免过早设计。

原则4：工具不应该替创作者决定发布形态

工具只负责把"创作内容"导出成不同格式（网页HTML、未来的小游戏
包、未来的APK），创作者自己拿着导出的东西去对接微信小游戏的
广告分成/虚拟支付、应用商店的内购，这些变现渠道是平台方现成
提供的，工具不用重新发明，也不该在中间做任何资金经手。

三、现有代码资产清单（用户本地已下载，路径供参考）
====================================================================

以下文件已经写好并做过验证测试，接手时应该复用而不是重写，
除非发现设计上的问题：

1. schema.md
   数据结构设计文档。定义了 Node 的 JSON 结构、interaction 的
   四种 type（choice / freeform / branch / next / end）、变量
   赋值和条件跳转的 JSON 表示、以及对应的文本语法（.lifeline
   格式）。这是整个项目的"契约文档"，改动数据结构时必须同步
   更新这个文件。

2. parser.js
   文本语法（.lifeline 格式）→ JSON 节点结构的解析器。
   纯函数实现，无外部依赖，可在 Node 和浏览器环境通用
   （导出用 module.exports，浏览器版把这行去掉直接内联即可，
   editor.html 里就是这么处理的）。
   已用多组测试用例验证：基础分支、delay 延迟、变量赋值、
   条件跳转、branch 分流、freeform 自由输入路由，均正确。

3. player.html
   独立可运行的播放器，单文件 HTML/CSS/JS，无构建依赖。
   核心能力：
   - 消息流 UI（视觉设计是"接收微弱信号的老式终端"风格，
     暗色+荧光绿，不是聊天软件仿制品，这是刻意的美术方向）
   - delay 延迟播放（demo阶段延迟做了压缩显示，真实产品需要
     换成真实等待+本地通知唤醒，见下方"已知缺口"）
   - 全局变量引擎：applySet / getVar / evalCondition / interpolate
     四个核心函数，运行时状态存在 `vars` 对象里
   - choice 模式渲染 + freeform 模式渲染（含"没有API Key时自动
     退化为选项模式"的降级逻辑，这个降级很重要不要删）
   - LLM 调用：目前只接了 DeepSeek 的 chat/completions 接口，
     API Key 从 localStorage 读取，从不发送到除 LLM 提供商
     之外的任何服务器

4. build.js
   命令行构建脚本，读取 .lifeline 文本，调用 parser.js，
   把结果 JSON 注入 player.html 模板，输出独立可运行的 HTML。
   这是"命令行版"的导出流程，editor.html 里的导出按钮是这个
   逻辑的浏览器内版本。

5. editor.html
   当前唯一的"编辑器"，单文件，双击可直接在浏览器打开使用。
   三栏布局：左侧节点列表（状态点：绿=正常/红=死路/黄=不可达）
   + 中间纯文本编辑区 + 右侧 iframe 实时预览（输入停顿350ms
   自动重新编译刷新）。
   内部把 parser.js 的逻辑和 player.html 的完整内容都内联
   进了一个文件（player.html 整体作为一个 JSON 字符串字面量
   注入，运行时用字符串替换塞入实际剧情JSON，生成 iframe 的
   srcdoc）。
   已知并修复过的坑：player.html 内部含有字面的 `</script>`
   文本（它自己的闭合标签），JSON.stringify 后如果不处理，
   浏览器的 HTML 解析器会在扫描 HTML 结构时把这个子串识别成
   外层 <script> 标签的结束，导致外层脚本被从中截断、语法报错。
   修复方式是在注入前把字符串里的 `</script` 替换成 `<\/script`
   （反斜杠转义拆开这个特征序列）。这是 HTML+JS 混合场景的
   经典坑，以后任何要把一段包含 <script> 的 HTML/JS 当字符串
   内联进另一个 <script> 标签的地方，都要做同样处理。

6. test-script.lifeline / test-branch.lifeline
   两个测试用例。前者是基础的 Lifeline 式坠机剧情（消息流+
   delay+choice+freeform）。后者是石之门式收束率剧情
   （变量+branch条件分流），验证了变量系统端到端可用。

四、数据结构核心定义（精简版，完整版见 schema.md）
====================================================================

单个节点：

{
  "id": "节点唯一标识",
  "messages": [
    { "speaker": "角色名", "text": "文字内容，支持{变量名}插值",
      "delay": 秒数, "set": { "变量名": "+5" } }
  ],
  "interaction": {
    // 四选一：
    // type: "choice" —— 固定选项
    "type": "choice",
    "prompt": "提示文字",
    "options": [
      { "label": "选项文案", "target": "目标节点id",
        "condition": "变量名 == 值（可选，不满足则此选项不显示）",
        "set": { "变量名": "+1" }（可选，选中后触发的变量变化） }
    ]

    // type: "freeform" —— 自由输入，LLM做意图路由
    "type": "freeform",
    "prompt": "提示文字",
    "system_prompt": "LLM的角色人设/边界约束",
    "routes": [
      { "intent": "意图描述（给LLM看，不是玩家看的文案）",
        "target": "目标节点id", "condition": "...", "set": {...} }
    ],
    "fallback": "都不匹配时兜底的目标节点id"

    // type: "branch" —— 不经过玩家操作，按变量自动分流
    "type": "branch",
    "rules": [ { "condition": "收束率 >= 80", "target": "结局_真" } ],
    "default": "兜底目标节点id"

    // type: "next" —— 线性推进，无选择
    "type": "next", "target": "下一个节点id"

    // type: "end" —— 结局，无更多内容
    "type": "end"
  }
}

条件表达式：仅支持单一比较 `变量名 运算符 值`，运算符为
== != > < >= <=，不支持 and/or 组合（如果后续要支持复合条件，
需要设计一个小型表达式解析器，目前特意做得简单）。

变量赋值语法：`+5`(相对增加) `=10`(直接赋值) `true`/`false`
(布尔值)，未定义变量默认值为数字 0。

====================================================================
五、.lifeline 文本语法速查（完整定义见 schema.md）
====================================================================

:: 节点名                          节点定义
角色名: 文字内容                    一条消息
[delay:5m]                        延迟标记(s秒/m分/h时/d天)，
                                   插在两条消息之间
[set 变量名:+5]                    独立一行，赋值给下一条消息
[set 变量名:=10] [set 变量名:true]  同上，赋值/布尔值写法

? 提示文字                         固定选项交互开始
  + 选项文案 -> 目标节点             一个选项
  + 选项文案 [if 条件] [set 变量:+1] -> 目标节点   带条件/赋值的选项

?? 提示文字                        自由输入交互开始
  system: 人设描述                 LLM system prompt
  ~ 意图描述 -> 目标节点             一条意图路由
  ~ 意图描述 [if 条件] [set 变量:+1] -> 目标节点
  fallback -> 目标节点              无法识别时兜底

[branch]                          条件分流块（不经过玩家操作）
  条件表达式 -> 目标节点
  default -> 兜底节点

-> 目标节点                        单纯线性跳转
-> END                            结局

行内可用 [set ...] [if ...] token，也可以独立成行（独立行的
[set] 作用于紧跟着的下一条消息）。

七、已知缺口 / 明确要做的下一步（按用户最新反馈排序）
====================================================================

【优先级最高，用户已明确要求】

1. 点击插入语法的工具栏
   现状：用户必须纯手打 .lifeline 语法，只有一个只读的"速查表"
   浮层可看，不能点击插入。
   需要做：编辑器里加一排快捷按钮/工具栏，例如：
   - 选中一段文字 -> 点"设为消息" -> 自动补全 `角色名: 文字`
     格式（角色名可以是输入框或记住上次用过的角色列表）
   - 点"插入选项" -> 在光标处插入一个 `?` + `+ ... -> ...`
     模板，并把光标定位到用户该填的位置（比如选项文案处）
   - 点"插入自由输入" -> 插入 `??` + `system:` + `~ ... -> ...`
     + `fallback` 模板
   - 点"插入延迟" -> 弹出时间选择（数字+单位下拉），插入
     `[delay:Nm]` 之类
   - 点"插入变量赋值" -> 弹出变量名+运算符+值的小表单，插入
     `[set 变量:+N]`
   - 点"插入条件分流" -> 插入 `[branch]` 模板
   实现建议：这类"在光标位置插入模板文本并选中待填部分"的
   交互，可以用 textarea 的 selectionStart/selectionEnd 结合
   一个"占位符 -> 自动选中"的小工具函数。也可以考虑升级成
   CodeMirror/Monaco 这类代码编辑器组件以获得更好的光标/
   自动补全能力（目前是原生 <textarea>，功能非常有限）。

2. 防呆校验
   现状：如果选项/路由的 target 指向一个不存在的节点名，
   parser.js 不会报错，只有运行到那一步预览才会显示
   "信号中断 — 节点缺失"。
   需要做：在 parseLifelineScript 之后增加一个校验步骤，
   检查所有 target/fallback/default 引用的节点id是否都在
   nodes 里存在，不存在则在 errors 数组里报出具体是哪一行、
   引用了哪个不存在的节点名。目前 errors 机制已经有雏形
   （parser.js 的 errors 数组，只是校验规则不全），扩展即可。
   建议同时校验：变量名拼写不一致（比如同一个变量在不同地方
   打错字导致实际是两个变量，创作者不容易发现）——这个可以
   做成"警告"而非"错误"，因为有时候是有意的新变量。

3. 变量实时面板
   现状：写 `[set 收束率:+50]` 时，创作者不知道当前收束率
   实际是多少，容易在长剧情里算错。
   需要做：编辑器界面上加一个"变量监视"面板，从起始节点开始
   模拟执行到当前光标所在节点，展示这条路径上所有变量的
   累积值。因为剧情是分支的，"当前值"取决于走了哪条路径，
   需要考虑清楚这个面板到底是：
   (a) 显示"从起点到当前节点，按文本顺序模拟一条路径"的值
       （最简单，但不一定是玩家实际会走的路径）
   (b) 让创作者手动选择"我现在预览的是哪条路径"，面板显示
       该路径下的变量值（更准确但交互复杂）
   建议先做 (a)，附带一个提示"这是假设从起点线性执行到此处
   的模拟值，实际取决于玩家的选择路径"，避免误导。

【次优先级，用户认可但排在插入工具栏之后】

4. 真正的项目/文件管理
   现状：编辑器只能编辑单个文本框内容，用 localStorage 存
   一份草稿，没有"项目"概念，没法管理多个故事、没有素材/
   角色库复用机制。
   需要考虑：是否要引入一个简单的本地项目结构（比如
   IndexedDB 存多个命名项目），允许创作者新建/切换/删除
   多个故事项目。这个改动会影响 editor.html 的整体状态管理，
   建议在做之前先评估是否要把编辑器从"单文件原型"升级为
   有构建流程的正式前端项目（见下方"技术栈建议"）。

5. 版本历史/撤销
   现状：写错了改坏了，只能靠浏览器撤销（Ctrl+Z），没有
   保存点机制，刷新页面前的修改如果没保存本地文件容易丢失
   （虽然有 localStorage 自动保存，但没有"回到10分钟前的
   版本"这种能力）。

6. 真实延迟通知机制
   现状：player.html 里的 delay 等待是压缩显示的假时间
   （demo阶段为了方便测试，最长只等6秒，倒计时文案显示的是
   原始时长）。真实产品需要：
   - 网页版：用 Notification API 或者浏览器 postMessage +
     setTimeout（真实时长）配合"离开页面后到点提醒"（可能
     需要 Service Worker 支持后台定时器）
   - 未来微信小游戏版：用小游戏的订阅消息能力，在用户离开
     时机推送"角色回复了"通知，这是小游戏生态原生支持的能力，
     比网页端更容易做好
   这块目前完全没做，是要提前想清楚方案的一块，工作量不小。

【用户提到但明确表示"以后需要时再加"，暂不要做】

7. 跨周目持久化
   支撑"死亡回归后记得上次选择""多周目才能拼凑全貌"这类
   机制。目前的原语（变量+条件跳转）只在单次游玩内有效，
   关闭页面/重新开始就清空。除非用户明确提出要写这类剧情，
   否则不要主动实现，避免过度设计。

====================================================================
八、技术栈现状与建议
====================================================================

现状：整个项目目前是无构建依赖的原生 HTML/CSS/JS 单文件方案，
没有用任何框架、没有 npm 依赖、没有打包工具。这是原型阶段
刻意的选择（图快速验证），继续往下做可能会遇到瓶颈：

- editor.html 已经 40KB+ 且用原生字符串拼接 DOM，功能继续
  增加（工具栏、变量面板、项目管理）后维护会越来越困难
- 原生 <textarea> 没有语法高亮、没有智能光标定位能力，做
  "点击插入语法"这类需求会比较别扭

建议接手时评估：是否要引入前端框架（React/Vue均可，用户之前
的 StoryCanvas 项目如果用过某个框架，优先保持技术栈一致）+
一个真正的代码编辑器组件（CodeMirror 6 是轻量且适合这种自定义
语法高亮场景的选择，Monaco 更重但功能更强）。这是架构层面的
决策，建议在开始做"工具栏插入"这个需求之前先定下来，避免
先在 textarea 上做一半又推倒重来。

播放器 player.html 保持无框架单文件是合理的，不需要跟着改，
因为它的运行环境是"打包给玩家的最终产物"，越轻量独立越好。

九、给接手编程助手的建议阅读顺序
====================================================================

1. 先读本文档第二节"核心设计原则"，理解为什么架构长这样
2. 读 schema.md 完整版，理解数据结构和语法的详细定义
3. 读 parser.js，跑一遍已有的测试用例（test-script.lifeline /
   test-branch.lifeline），确认理解解析逻辑
4. 读 player.html，重点看变量引擎四个函数和 playNode 主流程
5. 读 editor.html，注意 PLAYER_TEMPLATE 内联字符串的
   </script> 转义处理，这是唯一的"非显然"实现细节
6. 从本文档第七节"已知缺口"里选择任务开始开发，优先级已排序
